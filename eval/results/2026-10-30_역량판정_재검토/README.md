10/29 보고(`../2026-10-29_역량판정_일반화/`)를 올라온 결과 JSON으로 다시 계산하고, 다음 실험을 준비했다.
다시 계산하는 법: `webapp` 폴더에서 `npx vite-node scripts/ollama-fc.ts -- --score-only` (Ollama 없이 됨).

- 95% 구간: 자소서 20개를 다시 뽑는 부트스트랩 2000번 (`webapp/src/eval/cells.ts`).

## 2. 고칠 점

1. **용어**: 보고서의 "정확도"는 정밀도(precision)였음. 보고서와 검증 페이지를 "정밀도"로 고침.
2. **규칙만 F1 40%는 "전부 있음" 43%보다 낮음.** 95% 구간도 24%~53%로 넓어, 규칙만으로는 판정이라고 말하기 어려움.
3. **0.78을 다시 만들지 못함.** 같은 JSON에서 검증 페이지와 같은 식(후보 문장 점수 = 보정 점수 + 0.5 × 약한 서술)으로 계산하면 EXAONE 7.8B 후보 문장 AUC는 0.66 (95% 구간 0.58~0.74). 역량별 값(자원관리 1.00 등)도 다르게 나옴. 보고서 숫자를 만든 계산 파일이 필요함.
4. **진짜 자소서체(t01~t10)에서 더 나쁨.** EXAONE 7.8B 칸 AUC가 자소서체 0.69, 말투 0.83. 앱이 판정하는 건 자소서이므로, 말투 10개가 평균을 끌어올린 셈임.
5. **역량별 AUC는 쓰면 안 됨.** 정답이 2~5칸인 역량(자원관리 3, 수리 2)은 한 칸만 바뀌어도 크게 흔들림.
6. **선택지 B·C**: B(EXAONE)는 Ollama, 5GB 모델, 16GB 메모리가 필요해 "다른 사람 브라우저에서 바로 쓰는 웹앱"이라는 목표와 맞지 않음. C(Gemini)는 "자소서는 밖으로 안 보냄" 결정과 충돌함. 앱은 A(규칙만)로 두고, 결과 화면을 바꿈 (3장).

## 3. 이번에 바꾼 것

- **결과 화면**: 역량을 "있음/안 보여요"로 단정하지 않고, 자소서 근거 문장 후보를 보여 주고 사용자가 확인하게 함 (`webapp/src/main.ts` coverageHtml).
- **강제선택 판정 (실험용, 앱에는 안 씀)**: 역량마다 yes/no를 따로 묻지 않고, 문장마다 "10개 중 가장 잘 드러난 역량 하나, 또는 없음(X)"을 고르게 함 (`webapp/src/prep/judgeFC.ts`). 역량끼리 확률을 나눠 가지므로 한 문장이 여러 역량에 다 yes를 받기 어려움. 묻는 횟수도 자소서당 문장 수만큼(5번 안팎)으로 줄어듦 (지금 yes/no 방식은 약 25번).
- **재윤용 빈 라벨지**: `data/eval/라벨지_holdout_빈칸.csv`. 여진 정답을 안 보고 따로 붙이기.

## 4. 할 일

### 여진: 강제선택 측정 (Ollama가 있는 노트북)

```
ollama pull qwen3:1.7b
cd webapp
npx vite-node scripts/ollama-fc.ts -- --model qwen3:1.7b
npx vite-node scripts/ollama-fc.ts -- --model exaone3.5:7.8b
```

- 처음에 "연결 확인"에서 D(자기개발) 확률이 높게 나오면 정상. 끊기면 같은 명령으로 이어서 함.
- 끝나면 `webapp/_work/fc_요약.md`에 위 표와 같은 형식으로 강제선택 줄이 추가됨. 이 파일과 `_work/fc_*.json`을 보내 주면 됨.
- 판단 기준: Qwen3-1.7B 강제선택이 자소서체(t01~t10) 칸 AUC에서 EXAONE 7.8B yes/no(합의 정답 기준 0.74)를 넘으면 브라우저 안 모델로 앱에 넣을 가치가 있음. 못 넘으면 결과 화면은 지금처럼 "근거 후보"로 두고 마무리.

### 재윤: 두 번째 라벨

- `data/eval/라벨지_holdout_빈칸.csv`를 엑셀로 열고 역량 칸에 있으면 1, 없으면 0. 기준은 `eval/라벨기준.md`.

- 끝나면 kappa를 재고, 갈린 칸은 둘이 이야기해 정답을 정함. 그래야 "사람끼리도 갈린다"는 상한선 주장에 근거가 생김.

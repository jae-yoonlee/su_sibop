# 빠른 말 경고 (음절 방식) 측정 기록

2026-10-27 작성, 2026-10-30 실제 면접 답변으로 추가 검증. 상태: **개발 중**. 기준값은 바꾸지 않았다 (면접 데이터는 시험에만 씀).

## 왜 음절 방식인가
받아쓰기(Chrome) 글로 빠르기를 재면 말이 빠진 만큼 느리게 나온다 (실사용: 41초 답변 → 25단어).
그래서 소리만으로 음절을 센다. 한국어는 음절마다 모음이 하나라, 모음에서 여러 주파수 대역의 소리가 함께 솟는다.

## 비교한 방식 (FLEURS 한국어 낭독, 1.5배 빠르게 한 소리에서 잰 빠르기 비율, 정답은 1.42)

| 방식 | 1.5배 → 잰 비율 | 판단 |
|---|---|---|
| 대역 하나 소리 크기 봉우리 (de Jong & Wempe 2009) | 1.14 | 음절이 붙어 사라짐 (21% 손실). 버림 |
| 소리 변화량 봉우리 (스펙트럼 flux) | 1.13 | 같은 문제. 버림 |
| 소리 크기 리듬의 주파수 (변조 스펙트럼) | 1.11~1.16 | 변화를 못 따라감. 버림 |
| **여러 대역 상관 (Wang & Narayanan 2007)** | **1.34** | 채택 |

받아쓰기 없이 쓸 수 있는 다른 길: 이 PC 안 Whisper로 받아써서 글자 수 세기. 더 정확할 수 있지만 무겁고(모델 수백 MB), 사용자 결정이 '음절 방식'이라 보류.

## 결과 (채택 방식, 시험 문장 81개)
- 음절 수: 그대로 세면 25% 적게 셈 → 문장 읽기(31음절)로 사람마다 보정. 보정 뒤 평균 절대 오차 13.4%, ±10% 안 44%.
- **사람끼리 빠르기 비교는 못 함** (정답 빠르기와 상관 r=0.05). 그래서 고정 기준이 아니라 **내 문장 읽기 빠르기 대비 몇 배**로만 경고한다.
- 빠르기 변화는 따라감: 0.8배 → 0.83, 1.25배 → 1.19 (정답 1.21), 1.5배 → 1.34 (정답 1.42).
- 경고 흉내 (앞 6초 = 기준, 나머지 ≈5초, 기준 × 1.2 이상이면 빠름):

| 실제 빠르기 | 빠름 판정 |
|---|---|
| 1.0배 (오경보) | 4.9% |
| 1.25배 | 30% |
| 1.5배 | 50% |

배수를 1.1로 낮추면 1.5배 69%, 오경보 11.5%. 1.2를 유지했다 (알림 간격 규칙이 같은 경고를 45초에 한 번으로 막아도 오경보는 신뢰를 깎음).

## 실제 면접 답변으로 검증 (2026-10-30)
데이터: AI Hub 129 채용면접 인터뷰, Training 원천 wav 중 받아 둔 부분(01.Management)에서 나온 답변 **43개 (약 46분, 여 38·남 5)** + 정답 글.
즉흥 답변이라 '음·어' 같은 필러가 들어 있다. 기준값은 FLEURS로 정한 그대로 두고 시험만 했다. 원본은 저장소에 넣지 않음 (AI Hub 약관).

| | FLEURS 낭독 | **면접 답변** |
|---|---|---|
| 정답 빠르기 중앙값 (음절/말한 초) | 5.8 | **4.6** |
| 음절 수 평균 절대 오차 (보정 뒤) | 13.4% | **6.4%** (±10% 안 77%) |
| 답변끼리 빠르기 상관 | 0.05 | **0.70** |
| 1.5배 → 잰 비율 (정답 1.43) | 1.34 | 1.30 |
| 1.25배 → 잰 비율 (정답 1.21) | 1.19 | 1.16 |

답변이 1분 안팎으로 길어서 오차가 평균으로 줄어든다. 문장 하나(5~10초)였던 FLEURS보다 숫자가 좋은 이유 중 하나.

**앱 그대로 경고 흉내** (`scripts/pace-aihub.ts`): 같은 사람의 다른 답변 A를 기준(문장 읽기 대신)으로 두고 답변 B 전체를 PaceRule에 넣음. 104쌍.

| 답변 B | 경고가 뜬 답변 | 경고 켜진 시간 |
|---|---|---|
| 평소 빠르기 (실제로 1.1배 이상 빠르지 않은 93쌍) | **8% (오경보)** | 0.6% |
| 1.25배 빠르게 | **63%** | 15% |
| 1.5배 빠르게 | **88%** | 38% |

최소 기준 5.5음절/초를 빼면 1.25배 74%, 1.5배 98%로 더 잡지만 오경보도 13%가 된다. 면접 말투 평균이 4.6이라 5.5는 기준 × 1.2와 거의 같아서 큰 차이는 없다 → 그대로 둠.

이 검증의 한계:
- 화자 번호가 라벨에 없어서 **파일 번호가 붙어 있으면 같은 사람으로 가정**했다 (2개 이상인 묶음 9개).
- 기준을 1분짜리 답변 전체로 잡았다. 앱은 5~6초 문장 읽기라 기준이 더 흔들리고, 오경보는 이보다 높을 수 있다.
- 빨라진 말은 여전히 ffmpeg로 늘인 소리다.

5. 실제 브라우저·마이크로는 아직 안 돌려 봄.

## 다른 스레드에서 검증하는 법
```
# 1) FLEURS dev 받기 (앞쪽 약 260MB만)
curl -r 0-260000000 https://storage.googleapis.com/xtreme_translations/FLEURS102/ko_kr.tar.gz | tar xz
# 2) 빠르기별 소리 + Silero 확률 만들기
python -I webapp/scripts/pace-prep.py ko_kr <출력 폴더> webapp/public/vad/silero_vad_v5.onnx
# 3) 측정 (약 3분). --grid 붙이면 tune 절반으로 기준값 다시 고름 (오래 걸림)
cd webapp && npx vite-node scripts/pace-eval.ts <출력 폴더>
```
실사용 확인: 결과 화면에서 D 키 → 측정 정보의 `pace` (문장 읽기 음절 수·시간, 답변별 빠르기·기준).
면접 답변 재현: AI Hub 원천 wav + 라벨 JSON을 dev.tsv(번호, wav 이름, 답변 글, -, -, 길이, 성별)와 audio/dev/로 두고 위 2) 다음 `npx vite-node scripts/pace-aihub.ts <출력 폴더>`.
다음 단계: 일부러 평소/빠르게 두 번 답한 녹음 5명분 (진짜 빨라진 말 + 5초 문장 읽기 기준)으로 오경보·놓침을 재기.

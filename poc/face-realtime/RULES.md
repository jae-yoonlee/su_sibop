# AI 면접 코칭 설계서: 전체 흐름 · 판정 규칙 · 기준과 근거

작성일: 2026-10-05 (2차: 면접 흐름, 맞춤형 질문, 판정 근거와 참고 문헌 추가)

AI 면접 연습 한 번이 **어떤 순서로 진행되고, 그동안 무엇을 어떤 기준으로 판정하며, 그 기준을 왜 그렇게 잡았는지**를 한 문서로 정리했습니다. 지금 PoC에 이미 들어 있는 것과 앞으로 만들 것을 구분해 적었습니다. 측정값은 [SUMMARY.md](SUMMARY.md), [RESULTS.md](RESULTS.md)를 보세요.

읽는 순서: 1절(원칙) → 2절(전체 흐름) → 3절(판정 항목 표) → 4절(기준을 잡은 근거) → 5~7절(판정 방식, 표시 정책, 기술) → 8절(구현 순서) → 10절(한국어 대응) → 11절(평가 계획).

> **숫자에 대한 주의.** 이 문서의 기준값은 모두 초기값입니다. 4절에 항목마다 근거 수준을 표시했습니다. 논문이 뒷받침하는 것은 "무엇을 볼 것인가"와 "대략 어느 범위인가"까지이고, 정확한 숫자(예: 2초, 60%)는 대부분 직접 써 보며 맞춰야 하는 값입니다.

## 1. 원칙

1. **해석이 아니라 행동을 판정한다.** "긴장했습니다"가 아니라 "너무 빠릅니다!"처럼 듣자마자 고칠 수 있는 행동만 실시간으로 알린다. 그래야 기준을 숫자로 정할 수 있고 경고 문구가 바로 나온다.
2. **실시간 경고는 규칙으로만 한다.** 이 PoC에서 잰 값으로 Gemini는 한 번에 약 2초(들쭉날쭉), MediaPipe + 규칙은 15ms다. AI는 질문 만들기와 답변 후 리포트에만 쓴다.
3. **사람마다 다른 것은 본인 기준으로 본다.** 카메라 위치, 말 빠르기, 목소리 크기는 시작할 때 잰 본인 값과 비교한다.
4. **순간값으로 판정하지 않는다.** 모든 규칙은 기준을 넘은 상태가 일정 시간 이어질 때만 인정한다(필터).
5. **경고는 드물게 띄운다.** 말하는 도중의 잦은 알림은 방해가 된다 [8]. 걸린 경고를 언제 띄울지는 별도 정책(6절)이 정한다.
6. **범위는 AI 면접(앉아서 웹캠 정면)이다.** 발표는 청중을 둘러보는 것이 좋은 행동이라 기준이 반대인 항목이 있다. 기준값을 한곳에 모아 두고, 발표 모드는 나중에 기준표만 바꿔 추가한다.

시간(30초 / 2분 / 10초)은 설정값으로 둔다. 근거는 4.4절.

### 2.3 맞춤형 질문 3개

**입력**: 지원 직무(필수), 회사·업종(선택), 자기소개서 또는 이력 요약(선택, 붙여넣기).

**질문 구성** (구조화 면접의 질문 유형을 따른다 [12][13])

| 번호 | 유형 | 예시 | 맞춤 재료 |
|---|---|---|---|
| 1 | 지원 동기·자기소개형 | "○○ 직무에 지원한 이유와 본인이 맞는 이유를 말해 주세요." | 직무, 회사 |
| 2 | 과거 경험형 (실제로 했던 일) | "자기소개서에 쓴 △△ 프로젝트에서 가장 어려웠던 점과 해결 과정을 말해 주세요." | 자기소개서의 구체적 경험 |
| 3 | 상황 가정형 (이럴 때 어떻게 할지) | "마감 직전에 팀원이 맡은 부분이 안 됐다면 어떻게 하시겠어요?" | 직무에서 흔한 상황 |

**만드는 방법**: Gemini에 입력 내용과 위 유형 규칙을 주고, 질문 3개를 정해진 형식(JSON)으로 받는다. 한 질문은 2분 안에 답할 수 있는 크기로, 한 번에 한 가지만 묻도록 지시한다.

**안전장치**

- AI 호출이 실패하거나 10초를 넘기면 기존의 기본 질문 목록에서 유형별로 하나씩 고른다. API 키가 없어도 연습은 된다.
- 자기소개서 내용은 Google 서버로 전송된다. 입력 칸에 이 사실을 표시하고, 입력하지 않아도 진행되게 한다.
- 영상은 지금처럼 PC 밖으로 나가지 않는다.

**다음 단계(나중에)**: 2·3번 질문을 앞 답변 내용에 따라 꼬리 질문으로 바꾸기. 답변을 글자로 바꾸는 기능(STT)이 먼저 필요하고, 휴식 10초 안에 변환과 생성이 끝나는지 재 봐야 한다.

판정하지 않기로 한 것

- **깜빡임 → 긴장**: 쉬고 있을 때 1분 17회, 대화할 때 26회가 평균이다 [9]. 말만 해도 깜빡임이 늘어나므로 "1분 25회 초과 = 긴장" 규칙은 평범하게 말하는 사람에게도 걸린다. 이 PoC에서 잰 평소 값(17~18회)도 같은 논문의 쉬는 상태 평균과 일치한다. 횟수만 기록한다.
- **목소리 떨림·높이**: 스트레스를 받으면 목소리 높이가 올라가는 경향은 보고되어 있다 [7]. 하지만 노트북 마이크로 실시간 측정하면 오탐이 많을 것으로 예상해 경고에서 뺀다. 리포트용으로만 검토한다.
- **"내용에 오류가 있습니다!" 실시간 경고**: 판정이 2초 이상 늦고, AI가 틀리게 지적할 수 있으며, 말하는 도중의 내용 지적은 흐름을 끊는다. R2처럼 답변 뒤에 보여 준다.

## 4. 기준을 어떻게 잡았나: 근거

### 4.1 근거 수준

| 표시 | 뜻 |

| 깜빡임 제외 | **논문 + 실측**: 대화만 해도 깜빡임이 약 2배로 는다 [9]. PoC 실측과 일치 | - |
| 경고를 드물게 (6절) | **논문**: 말하는 동안 계속 보여 주는 피드백보다 드문 피드백(20초 쉬고 3초 표시)에 참가자 만족도가 높았다 [8] | 6절 참고 |

### 4.3 솔직하게 적어 둘 점

1. **"말이 빨라지면 긴장"은 근거가 약하다.** 발표 불안 연구에서는 불안이 높을수록 오히려 말이 느려지고 쉼이 늘었다 [10]. 그래서 "너무 빠릅니다!"는 긴장의 신호가 아니라 **전달력 문제**(듣는 사람이 따라가기 어려움)로 다루고, 긴장 구간(R3)은 말 막힘과 군말을 중심으로 본다.
2. **면접 연구는 대부분 대면·영어권 연구다.** 화상 면접, 한국어 면접에서도 같은 관계가 나오는지는 확인되지 않았다.
3. **관련이 있다는 것이지 원인이라는 뜻은 아니다.** "눈 맞춤을 늘리면 합격률이 오른다"까지 증명된 것은 아니다.
4. **참고 문헌은 초록과 요약 수준에서 확인했다.** 서지 정보(저자·연도·학술지)와 핵심 결과는 검색으로 확인했지만 본문 전체를 읽은 것은 아니다. 보고서나 발표에 숫자를 인용하기 전에 원문을 확인해야 한다.

### 4.4 흐름(시간, 질문 수)의 근거

| 설계 | 근거 |
|---|---|
| 질문 보기 30초 | **논문**: 실제 비대면 녹화 면접(AVI) 서비스 사용 기록을 분석한 연구에서 준비 시간 중앙값이 30초였다 [15] |
| 답변 2분 | **논문**: 같은 연구에서 답변 시간은 평균 약 2분, 가장 많이 쓰인 설정이 120초(질문의 51%)였다 [15] |
| 질문 3개 | **선택**: 같은 연구에서 실제 면접은 보통 4~5문항이었다 [15]. 연습용으로는 한 번에 9분 안쪽이 되도록 3개로 줄였다. 설정으로 늘릴 수 있게 한다 |
| 휴식 10초 | **가정**: 근거를 찾지 못했다. 숨 고르기와 다음 질문 준비용 |
| 유형이 다른 질문 3개 | **논문**: 구조화 면접(정해진 질문, 같은 기준)이 선발 도구 중 예측력이 가장 높게 나왔다(평균 타당도 .42) [12]. 과거 경험형과 상황 가정형은 구조화 면접의 대표 질문 유형이다 [13] |

## 5. 규칙 판정 방식

모든 규칙은 같은 네 단계를 거친다.

```
① 신호      프레임(1/30초) 또는 소리 조각(0.03초)마다 숫자를 얻는다   예: 좌우 각도 +27°
② 조건      숫자가 기준을 넘었는지 본다                              예: |27°| ≥ 20° → 참
③ 필터      참인 상태가 정해진 시간 이어져야 '걸림'으로 인정한다       예: 2초 유지
④ 표시 정책 걸린 경고를 지금 띄울지, 기다릴지, 리포트로만 남길지 정한다  (6절)
```

### 5.1 층 구분

| 층 | 판정에 걸리는 시간 | 해당 항목 | 방식 |
|---|---|---|---|
| 즉시 | 0.1초 이내 (+ 유지 시간) | V1~V5, A2 | 매 프레임 값에 규칙 적용 |
| 묶음 | 5~10초 | V6, A1, A3 | 최근 N초 구간의 평균·횟수에 규칙 적용 |
| 사후 | 답변이 끝난 뒤 수 초 | R1~R3 | 음성을 글자로 바꾼 뒤 집계, AI 검토 |

### 5.2 필터 (튀는 값 걸러내기)

| 필터 | 내용 | 쓰는 곳 |
|---|---|---|
| 유지 시간 | 조건이 연속으로 참인 시간이 기준(예: 2초)을 넘어야 인정 | 모든 즉시 규칙 (구현됨) |
| 짧은 끊김 무시 | 얼굴 인식이 0.5초 이내로 끊기면 타이머를 그대로 둠 | V1, V2 (구현됨) |
| 구간 평균 | 최근 10초 구간의 평균·횟수로 판정 | V6, A1, A3 |
| 켜짐·꺼짐 기준 분리 | 켜지는 기준보다 꺼지는 기준을 낮게 둬서 경계에서 깜빡이지 않게 함 | 말하는 중 판정(구현됨), A1, A3 |

### 5.3 영상 규칙 상세

**V1 고개 돌림 · V2 고개 숙임** (구현됨, `step3_coaching.py`)

- 신호: MediaPipe가 주는 머리 회전 행렬에서 좌우(yaw)·위아래(pitch) 각도를 계산하고, 카메라 맞추기에서 잰 "화면을 볼 때의 각도"를 뺀다.
- 조건: `|yaw| ≥ 20°` 또는 `pitch ≥ 15°`
- 필터: 2초 유지. 얼굴 인식이 0.5초 이내로 끊겨도 타이머 유지. 풀린 뒤에도 1초 더 표시.
- 한계: 눈만 돌리는 것은 못 잡는다(→ V5). 30~40° 이상 돌리면 인식이 끊긴다.

**V3 자리 이탈** (구현됨)

- 조건: 얼굴이 잡히지 않음. 필터: 2초 유지. 6절의 타이밍 정책 없이 바로 띄운다.

**V4 몸 치우침** (구현됨, 임시 기준, `coach_engine.py`)

- 배경: 정면을 본 채 몸만 옆으로 옮겨도 카메라에는 얼굴 옆면이 더 보여 yaw가 커진다. 그대로 두면 "정면을 보세요!"가 잘못 뜬다.
- 신호: 얼굴 중심의 가로 위치(화면 폭 대비 0~1). 카메라 맞추기 때의 위치를 기준으로 저장.
- 조건: `|현재 위치 − 기준 위치| > 0.12`. 이 동안의 yaw는 고개 돌림으로 세지 않는다. 필터: 2초 유지.
- 남은 일: "정면을 본 채 몸만 좌우로 이동"한 기록을 재서, 위치에 따른 yaw 오차를 직접 빼 주는 보정으로 바꾼다.

**V5 시선 이탈** (예정)

- 신호: MediaPipe가 이미 내주는 표정 점수 중 눈 방향 8개(`eyeLookIn/Out/Up/Down` × 좌우 눈, 각 0~1)를 좌우·위아래 두 값으로 합친다. 새 모델이 필요 없다 [17].
- 조건: 고개가 정면 범위(V1·V2에 안 걸림)인데 눈 방향 값이 기준을 넘음. 기준은 카메라 맞추기에서 "렌즈를 볼 때"와 "화면 가장자리를 볼 때"를 재서 그 사이로 정한다.
- 필터: 2초 유지. 눈을 감은 프레임(깜빡임 점수 0.5 이상)은 계산에서 뺀다.
- 위험: 안경 반사, 어두운 조명에서 값이 흔들린다. 정확도를 먼저 재 본 뒤 경고로 쓸지 정한다.
- 주의: 질문을 읽으려고 화면을 보는 것은 정상이다. 기준 방향은 "렌즈"가 아니라 "렌즈~화면 가운데" 범위로 잡는다.

**V6 몸 흔들림** (예정)

- 신호: 얼굴 중심 가로 위치의 최근 10초 기록.
- 조건: 방향이 바뀐 횟수로 왕복을 센다. 폭이 화면의 4% 미만인 움직임은 세지 않는다. 3번 이상 왕복이면 걸림.

### 5.4 음성 규칙 상세

공통 입력은 지금 있는 마이크 처리(`speech_state.py`)다. 0.03초마다 음량(RMS)을 계산하고, 시작 1초 동안 잰 주변 소음의 3배를 넘으면 "말하는 중", 2배 아래로 0.3초 이어지면 "조용함"으로 본다.

본인 기준(A1, A3 공통): **첫 질문 답변에서 처음 말한 20초**의 평균 음량과 평균 말 속도. 이 20초 동안은 A1·A3 경고를 띄우지 않는다. 2·3번 질문에서는 1번에서 잰 기준을 그대로 쓴다.

**A1 목소리 작음** (예정)

- 신호: "말하는 중"인 조각들의 음량만 모아 최근 5초 평균을 낸다.
- 조건: 본인 기준의 60% 미만이면 켜짐, 75%를 넘으면 꺼짐.
- 한계: 마이크와의 거리가 바뀌면 같이 변한다. V3·V4가 걸린 동안에는 판정하지 않는다.

**A2 말 막힘** (예정)

- 신호: "조용함"이 이어진 시간.
- 조건: 답변을 시작한 뒤(한 번이라도 말한 뒤) 침묵이 4초 이상.
- 표시: 생각을 정리하는 침묵일 수 있으므로 빨간 경고가 아니라 약한 안내로 띄우고, 리포트에 횟수와 가장 긴 침묵을 남긴다.

**A3 말 빠름** (예정, 2단계로 진행)

- 1단계 (글자 변환 없이): 음량의 오르내림에서 봉우리를 세어 음절 수를 어림한다 [14]. 한국어는 음절마다 모음이 하나씩 있어 이 방법이 맞기 쉽다. 최근 10초의 "말한 시간"당 봉우리 수를 분당 음절 수로 환산한다.
- 조건: 분당 400음절 이상, 또는 본인 기준보다 25% 이상 빠름. 본인 기준 +10% 아래로 내려오면 꺼짐.
- 검증: 대본을 읽어 실제 음절 수를 아는 녹음으로 추정값의 오차를 잰다. 오차가 15%를 넘으면 2단계로 간다.
- 2단계 (글자 변환 사용): 음성을 글자로 바꿔 글자 수를 센다. 정확하지만 1~3초 늦는다.

### 5.5 사후 규칙 상세 (예정)

- 답변이 끝나면(휴식 10초 동안 시작) 녹음을 글자로 바꾼다.
- **R1 군말**: 글에서 "음", "어", "그", "저", "뭐" 같은 군말을 세어 1분당 횟수로 낸다.
- **R2 내용 검토**: 질문과 답변 글을 AI에 보내 "질문에 답했는지, 사실과 다른 부분, 앞뒤가 안 맞는 부분"을 근거 문장과 함께 받는다. AI의 지적은 틀릴 수 있으므로 "오류"가 아니라 "확인해 보세요"로 표시한다.
- **R3 긴장 구간**: 한 가지 신호만으로 긴장이라 하지 않는다(4.3절). 같은 30초 구간에 말 막힘과 군말이 함께 늘었을 때를 기본으로 하고, 말 속도·음량이 본인 기준에서 크게 벗어난 것이 겹치면 더 확실한 구간으로 표시한다.

## 6. 표시 정책: 걸린 경고를 언제 띄우나

구현됨 (`feedback_gate.py`). 규칙이 "걸림"으로 판정한 경고를 그대로 다 띄우면 말하는 데 방해가 되므로 아래 정책을 거친다. 말하기 실시간 코칭 연구 [8]의 "드물게 띄우는 쪽이 낫다"는 결과와 같은 방향이고, 그 연구의 설정(20초 쉬고 3초 표시)과 값도 비슷하다.

| 정책 | 값 |
|---|---|
| 말하는 중에는 새 경고를 띄우지 않고 기다림 | - |
| 말을 멈춘 뒤 이 시간 사이에만 띄움 | 0.7~1.5초 |
| 아직 한 번도 말하지 않았으면 | 바로 띄움 |
| 기다리는 동안 스스로 고치면 | 띄우지 않고 버림 |
| 기다릴 수 있는 최대 시간 (넘으면 리포트로만) | 8초 |
| 경고 한 번의 표시 시간 | 2초 (다시 말하기 시작하면 바로 내림) |
| 경고 사이 최소 간격 | 20초 |
| 같은 종류 경고 사이 최소 간격 | 45초 |
| 1분 동안 최대 경고 수 | 2개 |
| 한 번에 띄우는 경고 수 | 1개 |
| 얼굴이 안 보일 때 | 정책 없이 바로 띄움 |

2분 답변 기준으로 경고는 최대 4개쯤 뜬다. 나머지는 리포트에 남는다.

음성 경고(A1, A3)를 추가할 때 정할 것: "너무 빠릅니다!"는 말하는 **중**에 떠야 의미가 있다. 음성 경고는 "말을 멈춘 순간에만" 조건에서 빼고 간격·횟수 제한만 적용하는 것을 기본으로 한다.

우선순위(여러 개가 동시에 걸렸을 때): 얼굴이 안 보여요 > 가운데로 앉아 주세요 > 정면을 보세요 > 고개를 드세요 > 카메라를 보세요 > 너무 빠릅니다 > 목소리가 작아요 > 몸이 흔들려요.

|---|---|---|
| PC 안에서 돌리는 모델 (예: Whisper 계열) | 무료, 음성이 밖으로 안 나감 | 설치 용량이 크고, 노트북 CPU에서는 느릴 수 있음. 속도를 재 봐야 함 |
| 클라우드 API (예: Gemini에 음성 전달) | 설치 없음, 빠르고 정확 | 비용, API 키 필요, 음성이 외부 서버로 나감 |

### 7.1 데이터 흐름

```
직무·자기소개 ─→ Gemini ─→ 질문 3개 ─→ 단계 진행기 (30초 → 2분 → 10초, 3회)
                                              │ 답변 단계에서만 아래 판정을 켠다
웹캠 (30 FPS) ─→ MediaPipe ─→ 각도·위치·눈 방향 ─┐
                                                  ├─→ 규칙 (조건 + 필터) ─→ 표시 정책 ─→ 화면의 빨간 경고
마이크 (0.03초 조각) ─→ 음량·말하는 중·음절 수 ──┘                          └─→ 기록
       └─→ 답변 녹음 ─→ STT ─→ 글자 ─→ 군말 집계 / Gemini 내용 검토 ─────────────┴─→ 질문별 리포트 → 종합 리포트
```

밖으로 나가는 것: 입력한 직무·자기소개 글, (클라우드 STT를 고르면) 답변 음성, 답변 글. 영상은 나가지 않는다.

### 7.2 시작할 때 본인 기준 맞추기

| 단계 | 재는 것 | 쓰는 곳 | 상태 |
|---|---|---|---|
| 위치 맞추기 | 얼굴 크기·위치가 적당한지 | 안내만 | 구현됨 |
| 렌즈 2초 보기 | 카메라 기준 각도, 카메라 높이 진단 | 안내 | 구현됨 |
| 화면 2초 보기 | 정면 각도(0°), 얼굴 가로 위치 | V1, V2, V4 | 구현됨 |
| (추가) 화면 가장자리 보기 | 눈 방향 점수 범위 | V5 | 예정 |
| 주변 소음 1초 | 소음 크기 | 말하는 중 판정 | 구현됨 |
| (추가) 첫 답변의 처음 20초 | 평소 음량, 평소 말 속도 | A1, A3 | 예정 |

알려진 문제: 지금 맞추기는 얼굴이 2초만 가만히 있으면 자동으로 넘어간다. 다른 곳을 보고 있어도 그 자세가 정면으로 저장될 수 있다. "준비되면 버튼을 눌러 확정"으로 바꾸는 것을 권한다.

## 9. 아직 정하지 않은 것

1. STT를 PC 안에서 돌릴지, 클라우드로 보낼지 (7절).
2. 음성 경고를 말하는 중에 띄울지 (6절). 기본안은 "띄운다".
3. 카메라 맞추기를 버튼 확정 방식으로 바꿀지 (7.2절).
4. 질문 수와 시간을 사용자가 바꿀 수 있게 할지. 기본안은 3개 / 30초 / 2분 / 10초 고정으로 시작.
5. 자기소개서 입력을 받을지. 받으면 질문이 훨씬 구체적이 되지만 개인 정보가 외부 AI로 전송된다.
6. 발표 모드를 언제 추가할지. 지금은 면접만 다룬다.

## 10. 한국어 대응: 어디가 언어에 묶여 있고, 파인튜닝이 필요한가

결론부터: **대부분은 언어와 무관하거나 한국어 자료가 이미 있다. 파인튜닝을 검토해야 하는 곳은 "음성 → 글자 변환(STT)" 하나이고, 그것도 먼저 재 본 뒤 정한다.**

### 10.1 부품별 점검

| 부품 | 언어 영향 | 한국어 상태 | 필요한 조치 |
|---|---|---|---|
| 영상 판정 (V1~V6): MediaPipe | 없음. 얼굴 모양만 본다 | 그대로 사용 | 없음 (안경·조명 검증은 언어와 무관하게 필요) |
| 음량, 말 막힘 (A1, A2) | 없음. 소리 크기만 본다 | 그대로 사용 | 없음 |
| 말 속도 측정 (A3 1단계, 음절 봉우리 세기) | 방법은 언어와 무관하나, 논문에서 검증한 언어는 한국어가 아니다(네덜란드어 자료) [14] | 한국어는 음절마다 모음이 있어 원리상 잘 맞지만 검증된 적은 없다 | **검증** (대본 낭독으로 오차 측정). 파인튜닝 대상이 아님 (학습 모델이 아니라 계산식) |
| 말 속도 기준값 | 언어마다 다르다 | **한국어 논문 값 사용 중** [11a][11b] | 없음. 영어 기준(분당 단어 수)을 가져오면 안 된다 |
| 질문 생성, 내용 검토 (Gemini) | 한국어 지원 | 한국어로 지시하고 한국어로 받는다 | **품질 확인** (질문 20개쯤 만들어 어색한 표현·한국 채용 관행과 안 맞는 질문 비율 확인). 범용 모델이라 우리가 파인튜닝하는 대상이 아니고, 지시문과 예시로 맞춘다 |
| **음성 → 글자 변환 (STT)** | **크다** | 아래 10.2 | **측정 후 결정. 파인튜닝 후보** |
| 군말 목록 (R1) | 언어마다 다르다 | 한국어 군말("음", "어", "그", "저", "뭐", "이제", "약간") 목록을 직접 만든다 | 목록 작성. 한국어 자유 발화 자료의 군말 표시로 빈도 확인 가능 [18] |
| 판정 근거 (4절의 면접 연구) | 문화 영향 가능 | 면접 행동 연구 [1][2][3]는 영어권·대면 연구다. 눈 맞춤·말투에 대한 기대가 한국 면접에서 같은지는 확인되지 않았다 | **한국 사용자 검증** (8절 8번). 한국 면접 자료 [19]로 보완 가능 |

### 10.2 STT가 핵심인 이유

1. **범용 모델은 한국어 자유 발화에서 영어보다 오류가 많다.** 대표적인 공개 모델(Whisper large-v3)의 글자 오류율이 영어 약 4%, 한국어 자유 발화(KsponSpeech) 약 11%로 보고된 바 있다 [21]. 한국어 자료 약 1,000시간으로 파인튜닝하면 크게 좋아진다는 보고도 있다 [22].
2. **범용 모델은 군말을 지운다.** Whisper는 "음", "어" 같은 군말을 빼고 깔끔한 문장으로 적도록 학습되어 있다 [20]. 우리는 군말을 세야 하므로(R1) 이대로는 쓸 수 없다. 군말을 그대로 적도록 파인튜닝한 사례가 있고, 주요 군말 인식률이 7% → 63%로 오른 보고가 있다 [20 관련 연구].
3. 그래서 **STT는 "한국어 정확도"와 "군말 보존" 두 가지를 모두 재야 한다.**

### 10.3 쓸 수 있는 한국어 자료

| 자료 | 내용 | 쓸 곳 |
|---|---|---|
| KsponSpeech [18] | 한국어 자유 대화 969시간, 약 2,000명. **군말·반복·말 끊김이 기호로 표시**되어 있다 | STT 파인튜닝과 평가, 한국어 군말 빈도 파악 |
| AI Hub 채용면접 인터뷰 데이터 [19] | 모의 채용 면접 음성 + 글자, 직군별(경영, 영업·마케팅, 공공, 연구개발, ICT 등), 감정·의도 표시, 요약 | 면접 말투에 맞춘 STT 평가·파인튜닝, 질문 예시, 답변 평가 기준 만들기 |

두 자료 모두 AI Hub에서 신청해 받는다. 이용 조건(상업적 이용 가능 여부, 국내 이용 제한)은 받기 전에 확인해야 한다.

### 10.4 파인튜닝 여부를 정하는 순서

1. **작은 시험 세트 만들기**: 본인과 2~3명이 면접 답변을 20~30분 녹음하고, 군말까지 그대로 받아 적는다.
2. **후보 재기**: 범용 모델(PC 안), 공개된 한국어 파인튜닝 모델, 클라우드 STT를 같은 세트로 재서 ①글자 오류율 ②군말을 살려 적는 비율 ③처리 시간을 비교한다.
3. **판단 기준(초기값)**: 글자 오류율 10% 이하이고 군말을 70% 이상 살리면 그대로 쓴다. 못 미치면 [18][19]로 파인튜닝한다.
4. 파인튜닝에는 GPU와 학습 시간이 필요하다. 노트북에서는 어렵고 클라우드 GPU를 빌려야 한다.

### 10.5 한국어를 차별점으로 만들 수 있는 판정 (제안)

영어 서비스에는 없는, 한국어 면접 말투에 특화된 사후 리포트 항목이다. 모두 글자로 바꾼 뒤 규칙이나 AI로 판정한다.

| 항목 | 예 |
|---|---|
| 한국어 군말 | "음", "어", "그", "이제", "약간", "뭐랄까" |
| 말끝 흐리기·추측 표현 남발 | "~인 것 같습니다", "~하지 않을까 싶습니다"가 답변의 절반 이상 |
| 격식체 일관성 | "~습니다"와 "~요"가 섞임, 반말 섞임 |
| 문장이 끝나지 않고 이어짐 | "~했는데, ~해서, ~하다 보니, ~" 한 문장이 30초 이상 |

이 항목들의 기준값은 [19]의 실제 면접 답변에서 빈도를 재서 정할 수 있다.

## 11. 평가 계획: 기능마다 정확도와 지연 시간을 잰다

과제명 "실시간 시선·filler word·발화속도 검출 시스템 구현 및 정확도/지연시간 평가"에 맞춰, 기능별로 **무엇을 정답으로 삼고, 어떤 숫자로 정확도와 지연을 보고할지** 정한다.

### 11.1 현재 상태 (2026-10-06 기준)

| 기능 | 구현 | 정확도 평가 | 지연 평가 |
|---|---|---|---|
| 시선 (눈동자) | 눈동자 방향 값(gaze_x, gaze_y)만 냄. 경고 규칙(V5)은 정확도를 본 뒤 | 5방향 측정 도구 있음 (`/eval.html`). **사람 측정 전** | 같은 도구가 지시 → 판정 지연을 냄. 측정 전 |
| filler word (군말) | 소리 기반(길게 끄는 "음—", "어—")만 됨 (`filler_detect.py`). 낱말 군말은 안 됨. 화면에 횟수 표시, 경고 카드는 아직 | 측정 도구 있음. TTS로만 확인. **사람 측정 전** | 설계값 0.33초, 처리 0.1ms/조각 |
| 발화 속도 | 됨 (`speech_rate.py`, 음절 봉우리 세기). 화면에 분당 음절 표시, "너무 빠릅니다!" 규칙은 모듈만 | 측정 도구 있음. TTS 낭독 6개에서 오차 −14~+7%. **사람 측정 전** | 10초 창이라 구조상 수 초. 측정 전 |
| 고개 돌림·숙임, 자리 이탈 | 됨 | 안 됨 (규칙 로직 테스트만 있음, 한 사람 실측으로 기준 정함) | 얼굴 분석 처리 시간만 잼 (15.4ms, 30 FPS). 경고가 뜨기까지의 지연은 안 잼 |
| 몸 치우침 | 됨 (임시 기준, PC에만 있음) | 안 됨 | 안 됨 |
| 작은 목소리, 말 막힘 | 규칙 모듈과 테스트만 있음 (GitHub). 화면 연결 여부 확인 필요 | 안 됨 | 안 됨 |
| 맞춤 질문 생성 | 모듈과 테스트만 있음 (GitHub) | 안 됨 | 안 됨 |

지금 있는 테스트(64개 + 저장소 추가분)는 "규칙이 코드대로 동작하는지"를 보는 것이고, "실제 사람의 행동을 맞게 잡는지"를 보는 정확도 평가가 아니다.

### 11.2 공통 방법

1. **정답 만들기 = 지시문 따라 하기.** 화면이 "지금 렌즈를 보세요", "지금 왼쪽 모니터 밖을 보세요"처럼 지시하고, 지시한 시각과 내용을 정답으로 기록한다. 사람이 영상을 보며 표시하는 것보다 빠르고 시각이 정확하다.
2. **녹화해서 다시 돌리기.** 평가 영상·음성을 파일로 저장해 두고, 같은 파일을 분석 엔진에 다시 넣는다(서버는 이미 웹캠 대신 영상 파일을 받을 수 있다). 기준값을 바꿀 때마다 같은 자료로 다시 잴 수 있다.
3. **정확도 숫자**: 잡아야 할 것을 잡은 비율(재현율), 잡은 것 중 맞은 비율(정밀도), 둘을 합친 F1. 그리고 **평소처럼 답변할 때 잘못 뜬 경고 수(분당)**. 마지막 숫자가 사용자 체감에 가장 중요하다.
4. **지연 숫자 두 가지**: ①처리 시간(입력 한 조각을 계산하는 데 걸린 시간, 평균과 상위 5%) ②검출 지연(행동이 시작된 시각부터 판정이 켜진 시각까지). 검출 지연에는 일부러 넣은 유지 시간(예: 2초)이 포함되므로 "유지 시간 포함/제외"를 나눠 적는다.
5. **사람과 조건**: 최소 3명, 안경 유무, 밝은 곳/어두운 곳. 지금까지의 기준은 한 사람 자료다.

| 정답 | 지시문: 렌즈 / 화면 가운데 / 화면 네 모서리(여기까지 정상) / 화면 밖 왼쪽·오른쪽·아래(이탈). 각 5초, 고개를 고정한 경우와 자유롭게 둔 경우 |
| 정확도 | 구간 단위로 "이탈"을 맞혔는지: 정밀도, 재현율, F1. 조건별(안경, 조명)로 따로 |
| 지연 | 처리 시간(ms). 지시가 바뀐 시각 → 이탈 판정이 켜진 시각 (사람의 반응 시간 약 0.3초 포함) |
| 목표 (초기값) | F1 0.85 이상, 평소 답변에서 잘못 뜬 경고 분당 0.5회 이하 |
| 못 미치면 | 실시간 경고에서 빼고 리포트용으로만 쓴다 |

**발화 속도 (A3)**

| | 내용 |
|---|---|
| 정답 | 음절 수를 아는 대본을 느리게·보통·빠르게 읽은 녹음(실제 분당 음절 수 = 음절 수 ÷ 시간). 자유 발화는 받아 적어서 음절 수를 센다 |
| 정확도 | 추정한 분당 음절 수와 실제 값의 평균 오차율(%), 상관. "너무 빠름" 판정의 정밀도·재현율 |
| 지연 | 처리 시간(ms). 대본 중간에 빨라지도록 읽고, 빨라진 시각 → 경고가 켜진 시각 (10초 구간 평균이라 구조상 수 초) |
| 목표 (초기값) | 평균 오차율 15% 이하 |
| 못 미치면 | 글자 변환(STT)으로 글자 수를 세는 방식으로 바꾼다 |

**filler word (R1)**

| | 내용 |
|---|---|
| 정답 | 면접 답변 녹음을 군말까지 그대로 받아 적고, 군말마다 시각을 표시한다 (20~30분 분량) |
| 정확도 | 군말 검출의 정밀도·재현율·F1 (횟수 기준, 그리고 시각이 ±0.5초 안에 맞는지 기준). 글자 변환 자체의 글자 오류율도 함께 |
| 지연 | 군말을 말한 시각 → 검출된 시각. 답변 후 처리라면 "답변 종료 → 결과"와 "음성 1분 처리에 걸린 시간" |
| 목표 (초기값) | F1 0.7 이상 |
| 정해야 할 것 | 과제명이 "실시간"이면 답변 뒤에 세는 방식으로는 부족하다. 방법은 둘이다. ①실시간 글자 변환(스트리밍 STT): 정확하지만 지연 1~3초, 비용·API 필요, 군말을 지우는 문제(10.2절) 확인 필요. ②글자 변환 없이 소리로 잡기: "음—", "어—"처럼 길게 끄는 소리(높이와 음색이 0.3초 이상 그대로인 구간)를 찾는다. 빠르고 PC 안에서 되지만 "그", "이제" 같은 낱말 군말은 못 잡는다 |

# 웹 배포형 AI 면접 코칭 설계안 (2026-10-09)

> 결론: **구현 가능합니다.** 영상 실시간 코칭은 웹으로 가도 어렵지 않습니다. 영상을 서버로 보내지 않고 **사용자 브라우저 안에서** 분석하면 지연이 거의 없습니다. 실제 어려운 부분은 영상이 아니라 **브라우저 안 로컬 AI(용량·사양)** 와 **한국어 받아쓰기(STT)** 입니다.

---

## 1. 무엇이 바뀌나

| | 기존 (su_sibop) | 새 구조 |
|---|---|---|
| 실행 | 재윤 PC의 Python + localhost | 아무 PC의 Chrome/Edge에서 주소만 열면 실행 |
| 얼굴 분석 | MediaPipe (Python) | **MediaPipe (웹 버전)**: 같은 랜드마크·같은 blendshape 이름이라 규칙 그대로 이식 |
| 음성 분석 | sounddevice + numpy | **Web Audio API (AudioWorklet)** |
| 로컬 AI | Ollama + EXAONE 3.5 | **브라우저 안 WebGPU 모델** + 실패 시 대체 경로 |
| 서버 | 없음 (PC가 서버) | 정적 사이트 + **Gemini 키를 숨기는 함수 1개**만 |
| 기록 | results/ 폴더 | **브라우저 IndexedDB** (계정·DB 없음) |

**가져오는 것은 "기술(규칙·기준값)"뿐입니다.** Python 코드는 TypeScript로 다시 씁니다. 판정 규칙은 단순한 상태 기계라 이식 위험이 낮습니다.

## 2. 기술별 비교와 선택

### 2-1. 얼굴·고개·중앙·자리 이동·눈동자

| 후보 | 장점 | 단점 |
|---|---|---|
| **MediaPipe Face Landmarker (웹)** ✅ | 기존 Python과 같은 모델·같은 값 → 기준값 재사용. 478점 + 52 blendshape + 머리 회전 행렬. WebGPU/WASM 둘 다 | 저사양 노트북에서 15fps 정도로 떨어질 수 있음 |
| TensorFlow.js face-landmarks-detection | 예전 자료 많음 | blendshape 없음 → 눈동자 값 다시 만들어야 함 |
| WebGazer.js (시선 추적) | 화면 좌표 시선 | 매번 보정 필요, 정확도 낮음, 유지보수 사실상 중단 |

**선택 이유:** 기존 기준값(아래)과 눈동자 계산식(`step2_face_landmarks.py`의 eyeLook* 조합)을 그대로 쓸 수 있는 유일한 후보.

재사용 기준값 (레포에서 추출):
- 고개 돌림 `YAW_LIMIT 20°`, 숙임 `PITCH_LIMIT 15°`, 유지 `HOLD_SEC 2s` (step3)
- 중앙 이탈 `CENTER_X_TOL 0.15`, 세로 `0.30~0.65`, 거리 `얼굴폭 0.18~0.45` (camera_setup)
- 자리 이동 `SHIFT_TOL 0.12` (coach_engine)
- 초기 세팅 `STEADY_SEC 2s`, `흔들림 3°`, `렌즈 vs 화면 각도차 12°` (camera_setup)

⚠️ 비판: **눈동자 움직임은 웹캠으로 "정확한 시선"이 아니라 "본인 기준 대비 흔들림 정도"만 믿을 만합니다.** 예전 기능 목록에서 정밀 시선을 뺀 이유와 같습니다. 기준값은 아직 데이터가 없으니 새로 측정해야 합니다.

### 2-2. 음량·소음·5초 침묵

| 후보 | 장점 | 단점 |
|---|---|---|
| **Web Audio RMS 규칙 + Silero VAD (웹)** ✅ | 기존 `speech_state`·`voice_rules` 그대로 이식. VAD가 키보드·소음을 말로 착각하는 것을 줄임 (모델 약 2MB) | VAD 지연 약 0.1~0.3초 |
| RMS 규칙만 | 가장 단순 | 주변이 시끄러우면 "말함" 판정이 흔들림 |
| 서버로 음성 전송 후 분석 | 강한 모델 사용 가능 | 지연·비용·개인정보 문제, 실시간 알림에 부적합 |

재사용 기준값: 작은 목소리 `내 기준보다 6dB 작음`(해제 4dB, 5초 유지), 말 감지 `소음의 3배`, 침묵 `STUCK_SEC 4s → 요청대로 5s`.

⚠️ **반드시 처리할 함정:** 브라우저 마이크는 기본으로 **자동 음량 조절(autoGainControl)·잡음 제거가 켜져 있습니다.** 켜 두면 "목소리가 작다" 규칙이 무의미해집니다. `getUserMedia`에서 `autoGainControl:false, noiseSuppression:false`로 꺼야 합니다.

새로 정할 값(데이터 없음): **주변 소음** = 말하지 않는 구간의 소음이 세팅 때보다 10dB 이상 커짐 (가설값, 실험 필요). **목소리 너무 큼**도 같은 방식.

### 2-3. 받아쓰기 (STT) — 꼬리질문·자소서 대조에 필수

| 후보 | 장점 | 단점 |
|---|---|---|
| **Web Speech API (Chrome)** ✅ 기본 | 무료, 실시간 스트리밍, 한국어 품질 양호, 설치 0 | **기본 모드는 음성이 Google 서버로 감.** Chrome/Edge 전용 (Firefox 미지원) |
| Whisper (transformers.js, WebGPU) | 완전 로컬 | small 약 590MB 추가 다운로드, 스트리밍 아님, base 이하는 한국어 정확도 약함 |
| 서버 Whisper/클라우드 STT | 정확 | 비용 발생, 무료 아님 |

**선택 이유:** "답변 끝나고 5초 안에 꼬리질문"은 **답변 중에 이미 글자가 나와 있어야** 가능합니다. 그걸 무료로 해주는 건 현재 Web Speech API뿐입니다.
⚠️ 비판: "로컬 처리"라는 주장과 충돌합니다. 화면에 **"음성 받아쓰기는 Google 서버를 거칩니다"** 를 명시해야 합니다 (기존 결정: 외부 전송 시 화면 표시). Chrome의 기기 내 받아쓰기 모드(`processLocally`, 언어팩 약 60MB)가 한국어를 지원하면 자동으로 그쪽을 씁니다 — 한국어 지원 여부는 **확인 못 함**, 실제 브라우저에서 확인 필요.

### 2-4. 필요역량 추출 (채용공고 → 역량)

| 후보 | 장점 | 단점 |
|---|---|---|
| **규칙 사전 + Gemini 정리** ✅ | 근거 단어가 남아 설명 가능. 공고는 공개 정보라 외부 전송 부담 없음 | 사전을 만들어야 함 |
| Gemini만 | 구현 최소 | 매번 결과가 달라지고 근거가 없음 |
| 로컬 LLM만 | 완전 로컬 | 작은 모델이 긴 공고 요약에 약함, 시간 소모 |

**사전 데이터:** **NCS 직업기초능력 10개 영역**(의사소통·문제해결·대인관계·조직이해 등)을 뼈대로 쓰면 "데이터 근거"가 생깁니다. 예: "사이좋게 지냈으면" → 대인관계능력(팀워크). 규칙이 근거 단어를 뽑고 → Gemini가 JSON으로 역량 3~5개 정리.
**자소서 대조:** 같은 사전으로 자소서에 근거 단어가 있는지 확인 (자소서는 외부로 안 보냄).
Gemini 키는 브라우저에 두면 유출되므로 **서버 함수 1개(Vercel/Cloudflare)** 로 감쌉니다.

### 2-5. 로컬 AI (질문 3개 생성) — 최신 재조사

| 후보 | 크기(첫 다운로드) | 한국어 | 라이선스 | 브라우저 실행 |
|---|---|---|---|---|
| **Qwen3-1.7B (WebLLM)** ✅ 기본 | 약 1GB, GPU 메모리 8GB 권장 | 119개 언어 학습 (한국어 품질은 직접 확인 필요) | Apache 2.0 | WebLLM에 이미 있음 |
| Qwen3-0.6B (WebLLM) | 약 0.5GB, 4GB | 질문 품질 낮을 가능성 큼 | Apache 2.0 | 바로 가능 |
| Kanana 1.5 2.1B (카카오) | 4bit 약 1.3GB 추정 | 한국어 특화 | Apache 2.0 (상업 가능) | **직접 변환(MLC/ONNX) 필요** |
| EXAONE 4.0 1.2B (LG) | 4bit 약 0.8GB 추정 | 한국어 특화 | **비상업 라이선스** | 직접 변환 필요 |
| Gemma 4 E2B (transformers.js) | 수 GB (4bit 실행 메모리 약 5GB) | 140+개 언어 | Apache 2.0 | 예제 있음, 너무 큼 |
| Chrome 내장 Gemini Nano (Prompt API) | 사이트는 0, Chrome이 2.7~4GB 받음 | 한국어 지원 **확인 못 함** | 무료 | 디스크 22GB·RAM 16GB 또는 VRAM 4GB 필요, Chrome만 |

**선택:** **Qwen3-1.7B로 시작, 한국어 질문 품질이 부족하면 Kanana 1.5 2.1B를 변환**해서 교체. EXAONE 4.0은 한국어는 좋지만 비상업 라이선스와 변환 수고 때문에 2순위.
이유: 지금 당장 브라우저에서 돌릴 수 있는 것 중 크기·품질 균형이 가장 낫고, Kanana는 "한국어 특화 + Apache"로 교체 후보로 명분이 좋음.

⚠️ **숨기면 안 되는 문제 3가지**
1. **첫 방문 1GB 다운로드.** 느린 인터넷이면 2분 이상 → "30초~1분 안에 질문" 목표를 첫 방문에는 못 지킵니다. 대책: **자료 입력 화면을 여는 순간 모델 다운로드 시작**(입력하는 동안 받음), 이후엔 브라우저 캐시로 수 초.
2. **WebGPU 없는 PC(구형·저사양·Safari 일부)는 실행 불가.** 대책: 시작 전에 자동 검사 → 안 되면 **Gemini로 대체(자소서 외부 전송 동의 받고)** 또는 **기본 질문 3개**(`question_gen.DEFAULT_QUESTIONS`).
3. **속도는 측정 전.** 내장 그래픽에서 토큰 속도는 공개 수치가 없어 직접 재야 합니다. 1주차 실험 항목.

### 2-6. 5초 안 꼬리질문 — 구체 제안

"답변 끝 → 5초"는 끝나고 나서 만들기 시작하면 작은 모델로는 빠듯합니다. **답변 중에 미리 만들어 두는 방식**으로 갑니다.

```
0s ──────────── 40s ────── 50s ────── 60s(답변 끝) ── +5s
   실시간 받아쓰기 누적
                 ① 규칙 검사(기존 followup_gen.find_issues):
                    숫자 불일치 / 숫자 누락 / 막연한 말 / '우리'만 있고 '제가' 없음 / 결과 없음
                 → 템플릿 꼬리질문 즉시 확보 (0.01초, 항상 성공)
                            ② 50초 시점 받아쓰기로 로컬 AI 호출 시작
                               "이 약점 하나만 골라 한 문장 질문" (최대 40토큰)
                                          ③ 답변 끝: 마지막 10초에 새 약점이 나왔는지 규칙 재검사
                                             AI 결과 있고 여전히 맞으면 → AI 질문
                                             아니면 → 템플릿 질문 (5초 마감 보장)
```
- 자소서 숫자 확인(불일치·누락)은 AI 없이 **규칙 질문 그대로** (기존 결정과 같음).
- 같은 자소서에서 이전 꼬리질문 피하기·관점 무작위는 기존 로직 재사용.
- 비판: 50초 이후에 처음 말한 내용은 AI 질문에 반영 안 될 수 있음 → ③의 규칙 재검사로 보완.

### 2-7. 자소서 vs 답변 객관 지표 대조

| 후보 | 장점 | 단점 |
|---|---|---|
| **정규식 추출 + 사용자 선택 + 유사도 비교** ✅ | 빠르고 결과가 매번 같음, 근거 표시 가능 | 고유명사 받아쓰기 오류에 약함 |
| LLM으로 추출·비교 | 표현 다양성 대응 | 없는 사실을 지어낼 위험, 매번 다름 |
| 한국어 개체명 모델 (KLUE-NER 등) | 정확도 높음 | 브라우저에 올리기 무거움 |

방식: 자료 입력 직후 자소서에서 **기간(년·개월·2023.03~), 역할(팀장·리더·담당), 프로젝트·논문명(따옴표·「」·"~프로젝트"), 숫자+단위**를 뽑아 체크박스로 보여주고 → **사용자가 비교할 항목을 고름**(요청하신 "고를 수 있게"). 답변 받아쓰기와 비교할 때 "삼 개월 → 3개월", "세 달 → 3개월"처럼 한글 숫자를 맞춘 뒤 비교.
⚠️ 비판: 받아쓰기가 프로젝트명을 틀리게 적으면 거짓 "불일치"가 납니다. 이름류는 **"불일치"가 아니라 "확인 필요"** 로 표시하고, 숫자류만 확정 판정합니다.

## 3. 실시간 알림 정책 — 결정 필요한 충돌

요청: 7가지 알림(작은 목소리, 소음, 5초 침묵, 고개 돌림, 중앙 이탈, 자리 이동, 눈동자)을 **실시간**으로.
기존 결정: 알림 간격 **20초**, 같은 종류 45초, **1분에 최대 2개**.
→ 답변이 60초라 **한 답변에 알림 최대 2~3개**만 뜹니다. 나머지는 **통계에는 전부 기록**되고 화면엔 안 뜹니다.
제 의견: 이 제한을 **유지**하는 게 맞습니다. 7개가 다 뜨면 답변 자체를 망칩니다. 우선순위는 `침묵·얼굴 안 보임 > 고개·중앙 > 목소리 > 소음·눈동자·자리 이동`.

**① 자료 입력** (그라디언트 배경)
- 큰 제목 "면접, 실전처럼" + 한 줄 설명
- 좌: 채용공고 붙여넣기 (자사 채용 설명) / 우: 자소서 붙여넣기 — `surface-indigo #1e2353` 카드, 16px
- 하단: 외부 전송 안내 배지(magenta) "채용공고만 Gemini로 전송 · 자소서는 이 PC 안에서만"
- 오른쪽 위 작은 칩: "AI 준비 중 34%" (모델 다운로드 진행)
- 초록 버튼 "분석 시작"

**② 준비** (카메라 전체 화면)
- 가운데 얼굴 가이드 타원, 위쪽 단계 카드(한 번에 하나): ① 가운데 앉기 → ② 카메라 렌즈 보기 → ③ 질문 나올 화면 보기 → ④ 정면 보기 → ⑤ 조용히 1초(소음 측정) → ⑥ 문장 읽기(목소리 기준, 너무 작거나 크면 안내)
- 왼쪽 아래 작은 진행 카드(백그라운드): 역량 정리 ✓ → 자소서 대조 ✓ → 질문 3개 만드는 중…
- **둘 다 끝나면** 얼굴 위 가운데에 큰 초록 "시작" 버튼

**③ 면접** (카메라 전체 화면, 오버레이만)
- 위: "1라운드 · 본질문" 배지 + 원형 타이머
- 질문 카드(가운데 위, `surface-indigo` 반투명 40px): 30초 표시 → 답변 60초 (타이머 색 Blurple)
- 알림 토스트(오른쪽 위, 2초): 짧은 명령형 "정면을 보세요", "목소리를 조금 크게"
- 왼쪽 아래 작은 음량 막대(기준선 표시)
- 답변 끝 → "꼬리질문 준비 중" (최대 5초) → 꼬리질문 30초 + 답변 60초
- 순서: 본질문1 → 꼬리1 → 본질문2 → 꼬리2 (질문 3개 중 2개 사용, 1개는 예비·다음 회차용)

**④ 리포트** (그라디언트 배경)
- 위 stat 카드 3개(Blurple): 역량 일치 % · 경고 n회 · 사실 일치 a/b
- 역량 표: 필요역량 / 자소서 근거 / 답변 근거 / 일치
- 경고 표: 종류별 횟수 + 질문별 타임라인
- 사실 대조: 고른 항목만 — 자소서 값 / 답변 값 / 일치·불일치·확인 필요
- 회차 비교: 직전 회차 대비 ▲▼
- 버튼: "리포트 저장"(Blurple) 아래 "다시 하기"(초록)
